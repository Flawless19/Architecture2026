ДЗ Неделя 4 - Базы данных для МаркетХаба - Индексы

# Контекст

МаркетХаб — маркетплейс с 50 000 зарегистрированных пользователей, 5 000 заказов в день и 200 000 карточек товаров. Технический стек: один сервер PostgreSQL с тремя основными таблицами — users, orders, products. Среднее время ответа: 80–120 мс. Система работает стабильно, но бизнес растёт.
## Как МаркетХаб выглядит изнутри:

Таблица products хранит 200 000 товаров. Поля: id, name (название, ~50 символов), description (описание, ~500 символов), category_id, seller_id, price, status (ACTIVE / INACTIVE / DRAFT). 80% товаров имеют статус ACTIVE.

Таблица orders — 3 миллиона записей. Поля: id, user_id, seller_id, status (NEW / PROCESSING / DELIVERED / CANCELLED), created_at, total_amount. Распределение статусов: 70% заказов — DELIVERED.
# Задание

Продуктовая команда МаркетХаба готовит три новые функции:

Функция A. Поиск товаров по каталогу: пользователь вводит в строку поиска «беспроводные наушники», система показывает релевантные результаты с ранжированием.

Функция B. Фильтрация заказов в личном кабинете: пользователь выбирает период дат и статус заказа («Оплачен», «В доставке», «Завершён»). Таблица orders сейчас содержит 3 миллиона записей.

Функция C. Отчёт для менеджеров по продажам: «Топ-100 продавцов по выручке за последние 30 дней». Отчёт строится раз в день по расписанию в 03:00.

Ваша задача: для каждой функции принять решение — какой тип индексной стратегии здесь нужен (или не нужен), и обосновать выбор.

Подсказка: для одной из трёх функций правильный ответ — «ничего не менять в существующих индексах».

3. Для функции B — дополнительно обоснуйте, почему при определённых условиях индекс по status может не использоваться планировщиком
    
### Формат сдачи

- Архитектурная схема: PlantUML / Miro / Excalidraw / от руки

### Что оцениваем

- Для функции C понято, почему вмешательство в индексы не нужно или даже вредно
    
- Понята проблема селективности для status
