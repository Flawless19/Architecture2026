# Ситуация

МаркетХаб расширяет функциональность. Команда продукта сформулировала четыре новых требования:

Требование A. Каталог товаров: разные продавцы продают разные типы товаров. Ноутбук имеет атрибуты: процессор, RAM, диагональ экрана. Платье имеет атрибуты: размер, цвет, материал, сезон. Обувь — размер, материал, высота каблука. Текущая схема products с фиксированными колонками не подходит: нужно хранить произвольные атрибуты для каждого типа товара.

Требование B. История действий пользователя: система должна хранить все события пользователей — просмотр товара, добавление в корзину, оформление заказа, поиск. Ожидаемый объём: 50 миллионов событий в месяц. Нужна фильтрация по user_id и временному диапазону.

Требование C. Рейтинг продавцов в реальном времени: «Топ-50 продавцов по числу завершённых заказов за сегодня» — обновляется каждую минуту, отображается на главной странице.

Требование D. Сессии пользователей и токены авторизации: хранить JWT-токены сессий. Нужен быстрый lookup по токену (< 5 мс), автоматическое истечение через 24 часа.

Ваша задача: для каждого требования предложить подходящее хранилище — PostgreSQL, MongoDB, Cassandra или Redis — и обосновать выбор.

Подсказка: для одного из требований правильный ответ — «оставить в PostgreSQL, NoSQL избыточен».

### Что оцениваем

- Правильно сопоставлен тип данных/запроса с хранилищем
- Понято, что Redis — это не «альтернативная БД», а инструмент для специфических задач (скорость, TTL, структуры данных)
- Понято, что Cassandra подходит для высокочастотной записи с простым access pattern
- MongoDB обоснованно выбран для гибкой схемы
- Осознана проблема «полизоглотного хранения» — не добавлять новые хранилища без явной причины

  
  

## Инструкция по выполнению

### Шаг 1. Задайте правильные вопросы по каждому требованию

Для каждого требования ответьте:

- Как структурированы данные? (Фиксированная схема / гибкая / «плоские» записи)
    
- Как читаются данные? (Точечный lookup / диапазон / агрегация)
    
- Каков объём? Какова нагрузка на запись?
    
- Нужна ли транзакционность (ACID)?
    
- Нужно ли автоматическое истечение данных (TTL)?
    
### Шаг 2. Соотнесите требования с характеристиками хранилищ

|   |   |   |
|---|---|---|
|Хранилище|Сильная сторона|Слабая сторона|
|PostgreSQL|ACID, сложные запросы, JOIN|Гибкость схемы, горизонтальная запись|
|MongoDB|Гибкая схема, документ = объект|Транзакции сложнее, нет JOIN|
|Cassandra|Высокая скорость записи, масштаб|Ограниченный query model, eventual consistency|
|Redis|Скорость (RAM), TTL, структуры данных|Объём данных ограничен RAM, не для сложных запросов|

### Шаг 3. Определите «ловушку» задания

Одно из требований намеренно выглядит как кандидат для NoSQL, но решается в PostgreSQL. Подумайте: какое именно, и почему добавлять новое хранилище будет избыточным?

### Шаг 4. Нарисуйте итоговую архитектуру

Нарисуйте общую схему МаркетХаба: API-сервисы и их зависимости от хранилищ. Для каждой стрелки укажите: что за данные передаются и в каком направлении.

### Шаг 5. Напишите обоснование

Особое внимание уделите обоснованию PostgreSQL-решения: почему в данном случае проще и надёжнее оставить данные там, где они уже есть, а не добавлять новую систему.
